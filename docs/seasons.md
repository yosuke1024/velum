# 季（シーズン）— 出来事を前もって組み立てる

1人につき5話、5人で25日分の出来事を、季の頭でまとめて計画する。

**実装状況:** 実装済み。`src/season/`、`npm run plan`。

---

## 1. なぜ前もって作るのか

出来事をその日に即興で作ると、**物語の形がどこにもない**。

毎日その場でひとつ出来事を作らせると、モデルは「今日は何が起きるか」だけを考える。発端も転機も決着もなく、昨日の設定を今日が壊す。5日経っても物語が始まらないか、5日とも別方向へ散る。

だから先に5話ぶんを組み立てる。

```text
第1話 発端  問題が具体的な形をとる。まだ引き返せる。
第2話 展開  話が込み入る。単純だと思っていたことが単純でなくなる。
第3話 転機  何かが変わる。前の2話の前提がひとつ崩れる。
第4話 危機  逃げ道がなくなる。選ばなければならなくなる。
第5話 決着  片がつく。ただし世界は終わらない。次の季へ残り火を置く。
```

もうひとつ、こちらのほうが大きい理由がある。**人間が読んで直せる。**

計画は `world/seasons/<季>/<時代>.yaml` に YAML で書き出される。走らせる前に25日分すべてを読み、気に入らない展開を書き換えられる。日ごとの即興ではこれができない——出てきたものを受け入れるか、その日を捨てるかしかない。

## 2. 1季 = 25日

ローテーションは5日で5時代を1周し、5周で1季が終わる。

```text
 1日目 ギルド 第1話    6日目 ギルド 第2話   ...  26日目 ギルド 第1話（第2季）
 2日目 静寂   第1話    7日目 静寂   第2話
 3日目 大収束 第1話    8日目 大収束 第2話
 4日目 破砕   第1話    ...
 5日目 原初   第1話          25日目 原初 第5話（第1季 終わり）
```

各主人公は1季のあいだに5話ぶんの日記を書く。読者は日付順に読むと5つの時代を毎日飛び回り、時代順に読むとひとりの物語を5話続けて追える。**同じ日記が、並べ方で別の意味を持つ。**

## 3. 何を渡して組み立てるか

```text
アーク（world/arcs/）
+ 未解決スレッド（このときは全部渡す。5話の形を作るには一望が要る）
+ 季の始まりの時点での人物状態
+ 前の季が残したもの（第5話の leaves_open）
+ イベントカード（world/cards/ から重み付きで7枚。素材であって出来事ではない）
+ 乱数（季ごとに決まる。同じ季を作り直しても素材は変わらない）
= 5話ぶんの出来事
```

カードは**素材**である。そのまま出来事にせず、アークと人物の状況に照らして具体化する。使わないカードがあってよいので、5話ぶんより多めに引く。

## 4. 世界は計画され、人物は反応する

前もって決めた出来事は、その人がどう変わったかに反応できない。これは避けられないトレードオフであり、次のように分けて受け止める。

| | 決まっているもの | 動くもの |
|---|---|---|
| 日ごと | 何が起きるか | どう受け取り、どう変わるか |
| 季ごと | — | 次の季の計画が、いまの状態から立てられる |

**人物が世界へ反応するのは日ごと、世界が人物へ反応するのは季ごと。** 25日に一度、その時点の人物状態を読んで次の季を組み立てるので、フィードバックは季の境目で入る。毎日反応させると、それは物語ではなくその日の気分の連鎖になる。

## 5. 暦 — 大きな流れに沿わせる

季の計画は Velum の暦の上に立つ（`world/canon/calendar.yaml`）。

- **1年 = 12の月 × 30日 + 五夜（どの月にも属さない5日）= 365日。** 月の名（芽の月〜眠りの月）は原初の星読み由来で、全時代共通。
- 各時代の**祭・節目**は `world/canon/<era>.yaml` の `observances` にある。仮銘審査、北の市、灯の日、星祭り——アークの時限装置はすべて暦の上の日付を持つ。
- 各時代の「いま」は `world/clocks.yaml`。**季の計画が立つたびに、最終話の翌日へ進む。**

### 日付は飛ぶ

各話は `world_date` を持ち、**日付は連続しない**。日記は毎日つけるものではない。季全体で20〜40日ほど進むのが目安で、この速さだと**現実の1年でおよそ世界の1年**が巡る。稼働開始時は全時代が星の月4日（秋の初め）——現実の9月と季節がゆるく重なって進む。

### 年の数え方は時代の声

| 時代 | 年 | 声 |
|---|---|---|
| 原初 | **数えない**（null） | 「星祭りまであと十一の夜」。日付の数字を使わない |
| ギルド | 375年 | 年月日。期限と台帳の暦 |
| 大収束 | **417年のまま変わらない** | 終わらない年。芽の月一日からの通算日「収束暦」を併記 |
| 破砕 | 656年（開戦から239年目） | 戦後を知らない世代の暦 |
| 静寂 | 1,175年 | ギルドとの差はちょうど八百年（ヴェスパーの首飾りの糸を数字で支える） |

## 6. canon との関係

`world/canon/<era>.yaml` の `fixed` は固定事実であり、**計画がこれと矛盾したら直す。** `npm run validate` が季の計画も検証するので、手で直したものが壊れていないかも見られる。

固定していない細部（通りの名前、通行人、天候、品物）は自由に作ってよい。即興された細部が繰り返し登場するようになったら、人間が canon へ昇格させる。

## 7. 出来事だけを書く

計画に書くのは「起きたこと」だけで、人物がそれをどう感じたかは書かない。感情・解釈・内面は、このあと本人が日記で書く（[diary.md](diary.md)）。

この分離が効くのは、**事実と主観を別の層に置くことで、日記が事実を上書きできなくなる**からである。日記の中で人物が何を思おうと、起きたことは計画に書かれたままである。

## 8. 時代を跨ぐ糸

`world/threads/cross-era.yaml` に5本の糸がある（聴き手の系譜・制度の系譜・ヴェスパーの首飾り・セヴランの記録帳・五夜）。

**計画のプロンプトへ「この糸を回収せよ」と指示していない。** 人物は自分が糸の一部であることを知らないまま生きる。糸は読者だけが横断して発見できる形で仕込まれており、それが公開リポジトリとしての読み物価値になる。

糸を動かすのは人間である。canon やアークを編集したときにだけ動く。

## 9. 使い方

```bash
npm run plan -- --season 1                 5時代ぶんまとめて計画する
npm run plan -- --season 1 --era guilds    1時代だけ作り直す
npm run plan -- --season 1 --force         計画済みでも上書きする
npm run validate                           直した計画が壊れていないか見る
```

計画を立てたら `world/seasons/001/` を読む。`shape` に、その5話でどういう形を描くのかが2〜3文で書いてある。直したい話があれば YAML を直接編集してよい。番号と beat の並びだけは崩さないこと（validate が落とす）。

### 季の境目

次の季の計画は自動では立たない（§1）。だから**次の季の初日の朝に計画が無ければ、その日から日次ジョブは毎朝赤くなる**——計画が入るまで日が欠け続ける。ここで黙って緑を返すほうが危ない。世界が止まったことに誰も気づかないまま日が過ぎるからである。

赤くなってから気づいたのでは、その日はもう欠けている。そこで季の残りが**最後の1周（5日）**に入ると、`npm run day` がまだ緑のうちに警告を出す。GitHub Actions では run の注釈にも残る。

```text
⚠ 第1季は残り5日。2026-09-26 から第2季が始まりますが、計画がまだありません（...）。
  その朝までに npm run plan -- --season 2 を回してください。
```

**警告が出てから立てればよい。** §4 のとおり、次の季はその時点の人物状態を読んで組み立てるので、早く立てるほど古い状態から作ることになる。最終日に近いほど、直前の5話が反映される。

## 10. 訳は、計画と同時に付ける

サイトは 1言語 = 1 URL である。時代ページ（`/velum/<時代>/`）が季の計画から出すのは **`title` / `shape` / 各話の `leaves_open` の3種類だけ**で、この3つは `{ ja, en }` を必須にしてある。

```yaml
title:
  ja: 座金の残影
  en: "The Washer's Afterimage"
```

**`npm run plan` が両方書く。** 応答が `title_ja` / `title_en`、`shape_ja` / `shape_en`、`leaves_open_ja` / `leaves_open_en` を返し、欠けていれば `SeasonPlanSchema` がその場で落とす。

以前は逆だった。生成は日本語だけを書き、訳は §9 のとおり人間が直したあとに付ける——生成と同時に訳を作ると、日本語を直した瞬間に英語だけが古くなり、公開ページに「読めるが内容の違う英語」が残るからである。**日本語のまま出ているほうが、まだ壊れていると分かる。**

その天秤は 2026-09-01 に傾いた。掲載側（pixapps-landing）に「ひとつの URL にはひとつの言語」を見るガードが入り、未訳の欄は見えている欠陥ではなく、**その日の公開が丸ごと止まる原因**になった。最初の日記が公開される朝、信念の名前が未訳だったせいで実際に同期が止まっている。数えて見せるだけでは、もう釣り合わない。

だから順番はこうなる。

```text
npm run plan（両言語）  →  人間が読んで直す  →  npm run validate
```

**古い順番が避けようとしていた問題は消えていない。** 日本語だけ書き換えれば、英語は古いまま公開ページに残る。validate は「訳が無い」ことは見つけられるが、「訳が古い」ことは見つけられない——訳が新しいかどうかは機械には分からない。**直す単位は「欄」であって「言語」ではない。** 日本語を直したら、その欄の `en` も同じ手で直すこと。

## 11. Narrative Calibration — 季ごとに2〜3個だけ許す

**実装:** `src/season/narrative-calibration.ts`（season-v3、2026-09-06）。

§1 の判断は変えない。出来事は前もって組み立てるし、5話の beat も固定のままである。変えたのは**その構造が毎季まったく同じように効くこと**のほうである。

season-v2 は「各話は前の話の結果の上に立つ」と書いていた。1季の物語を成立させるには効く。だがこれを既定にすると、5話は必ず一本の綺麗な因果鎖になり、決着は必ず主人公の理解で閉じる。25日 × 5時代を何季も回したとき、読んで退屈になるのは1季の出来ではなく、**全季が同じ形へ収束すること**である。

そこで、緩めてよい箇所を小さなカタログにして、**季ごとに2〜3個だけ**選んで渡す。

| id | 許すこと |
|---|---|
| `causal_sidewind` | 1話は、前の話の結果ではなく暦・第三者・制度・オフステージから動き出してよい |
| `external_driver` | 転機や決着を、主人公の選択だけで起こさなくてよい |
| `partial_resolution` | 第5話は片がつくが、理解・納得・成長で締めなくてよい |
| `delayed_recontextualization` | 既存の普通の情報を後の話で出し、前の出来事の見え方を変えてよい |
| `texture_without_payoff` | 後で回収しない小さな出来事・会話・物を1つ残してよい |
| `relationship_friction` | 関係を理解・和解の方向だけへ動かさなくてよい |
| `offstage_consequence` | 重要な結果の一部が、主人公の見ていないところで起きてよい |
| `asymmetric_depth` | 5話の密度を揃えなくてよい |

### 毎季すべては渡さない

これがこの仕組みの本体である。カタログを全部渡せば、「横道に逸れ、外部要因で決着し、関係がこじれ、回収しない小物が残る話」が毎季続く——**それは緩和ではなく、別のテンプレートである。** 一本道と、退屈さの種類が違うだけになる。

同じ理由で、渡すのは**許可であって指示ではない**。使わない季があってよい。

### 選択は seed から決まる

`season-<季>:<時代>` の seed から決まるので、同じ季を作り直せば同じ許可が出る。イベントカードと同じ約束である——やり直したときに「その季がどういう季だったか」まで変わってしまうと、失敗した季をやり直せない。

抽選は `${seed}:narrative` という**別の乱数の流れ**から引く。カードと同じ流れを使うと、カタログに1個足しただけで過去の季の引き札が変わる。`tests/unit/narrative-calibration.test.ts` がこの非干渉を見ている。

そのうえで二つ:

- **効かない許可は選ばない。** 周囲に人物のいない状況で「関係がこじれてよい」と許しても、モデルは辻褄合わせに人物を発明するだけである。
- **直前の季と丸ごと同じ集合は避ける。** 一部が重なるのは構わない。二季続けて同一だと、「この時代はそういう形」という別の型ができる。

### 選んだものは計画に残る

`generation.narrative_moves` に id が並ぶ。

```yaml
generation:
  model: gemini-3.5-flash
  prompt_version: season-v3
  seed: season-1:guilds
  narrative_moves:
    - asymmetric_depth
    - texture_without_payoff
    - partial_resolution
```

目的は二つ。再現性と、**人間が読むときの説明可能性**である。§9 のとおり計画は人間が読んで直すファイルなので、この季だけ第3話が横から動いているのは生成が滑ったからではなく、そう許可したからだと分かる必要がある。この欄は optional で、season-v2 で立てた `world/seasons/001/` はそのまま読める。

### これは何ではないか

考え方は [Sepia](https://github.com/Nanako0129/sepia) の Narrative Architecture / StoryScope 系の知見を参考にした**独自実装**である。Sepia を依存に持たず、判定器としても使わない。そして:

- **AI 文章検出器ではない。** 生成物に「AIらしさ」の点を付けない。
- **人間らしさの正解を強制するものでもない。** 渡すのは許可だけで、どう書けば人間らしいかは決めない。
- **生成後の書き直し工程を持たない。** humanize rewrite も、文体語彙の禁止リストも、文章の質を理由に日を破棄する新しいバリデータも足さない。Velum の正は引き続き `Season Plan + 構造化された人物状態 + canon` であり、日記はその主観表現である（§7）。

文章表現の側の対応は [diary.md](diary.md) §11。
