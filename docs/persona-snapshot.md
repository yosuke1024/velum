# Persona Snapshot

World と Diary の履歴から、PixTale が使う圧縮済みペルソナを生成する。

**実装状況:** 実装済み（M3）。`src/compile/`、`npm run snapshot`。
検収（§7）は日記が溜まってから行う——いま圧縮できるのは profile と canon だけである。

---

## 1. 何を圧縮するのか

PixTale へ日記の全文を渡すのではない。**人生の結果として残った人物像**へ変換する。

```text
出来事:
  親友に約束を破られた

人物への長期的な影響:
  - 口約束を信用しない
  - 書面や証拠を重視する
  - 親しい相手ほど慎重に距離を測る
```

Tale コメントに必要なのは後者だけである。前者は `characters/<id>/diaries/` に残っていればよい。

## 2. Snapshot に入るもの

- 基本人格（profile 由来の固定層）
- 時代・職業・立場
- 価値観
- 現在の人物状態（要約）
- 重要な人生経験（memories から importance 順に）
- 人間関係から形成された態度——**関係そのものではなく、関係が残した癖**
- 観察時の着眼点（`appraisal.question` / `focus`）
- 偏見・誤解
- 話し方（`voice`）
- 知識境界

## 3. Snapshot に入れないもの

- 日記の全文
- 他の時代・他の人物の情報
- `relationships.yaml` の `hidden_from_protagonist`（**本人が知らない事実は渡さない**）
- `core.secret_unknown_to_self`（同上。ただしその結果として現れる着眼点は入れる）

最後の2つが重要である。テオが「作り手の執念に反応する目」を持っていることを彼自身は知らない。Snapshot に入れるのは「量産品にすら作り手の物語を視てしまう」という**振る舞い**であって、その正体ではない。

## 4. バージョニング

```text
characters/<id>/snapshots/v0007.json
```

Snapshot は追記のみ。既存バージョンを上書きしない。

PixTale Proxy は**バージョンを固定して**読む。したがって:

- こちらの生成が止まっても、PixTale は動き続ける
- Diary 生成が壊れても、直近の安定版ペルソナが使われる
- 不自然な人格変化があれば、ピンを以前のバージョンへ戻すだけで元に戻る

```text
velum: characters/<id>/snapshots/v0007.json
         ↓ 公開ファイルとして取得
PixTale Proxy: KV へキャッシュ → 選ばれた時代と人物の分だけプロンプトへ注入
```

**実行時の連携はこの一方向のファイル取得だけ。** 両リポジトリはデプロイも CI も独立している。コード共有もサービス間連携も、この企画の目的ではない。共有するのは思想・データ形式・生成成果である。

## 4.5 生成を通すのは一箇所だけ

Snapshot のほとんどは生成の産物ではなく、**profile・canon・current-state・memories の射影**である。同じ材料からは同じものが出る（`tests/unit/snapshot.test.ts` が固定している）。

生成を通すのは `dispositions`——**人生が残した癖**——だけである。圧縮が必要なのがそこだけだからで、必要のないところまで生成に通せば、動かないはずの人格の芯が回すたびに揺れる。

| | 決まり方 |
|---|---|
| `identity` / `voice` / `appraisal` | profile の射影。生成は触れない |
| `values` / `temperament` / `standing` | current-state の射影。強い順に並べ替えるだけ |
| `life_facts` | canon の射影。formative_events は全件、追記は新しいものから |
| `remembered` | memories を importance 順に上位いくつか |
| `knowledge_boundary` | 時代の定義（`world/canon/eras.yaml`）の射影 |
| **`dispositions`** | **ここだけ生成** |

`appraisal.humor` は射影の側にある。ここが生成を経て「真面目な要約」に均されることは、構造上起こらない。

## 4.6 本人が知らないことは、二重に止める

除外は `src/compile/context.ts` の型で担保する。`CompileContext` は `secret_unknown_to_self` も `hidden_from_protagonist` も持たないので、生成へ渡す材料にそれらは存在しない。

そのうえで `src/compile/gate.ts` が、**出来上がった Snapshot を秘密の文面と照合する**。型で止まっているなら要らないように見えるが、止まらなくなるのはあとから profile や relationships をまるごと流し込む変更が入ったときで、そのとき壊れるのは CI ではなく PixTale が語る人格である。

ゲートはもうひとつ、**癖に関係者の名前が入っていないか**を見る。Tale コメントを読む側は、ヴァレンもロウも知らない。「師匠に言われたとおり」と書かれた鑑定文は、読者にとって意味を持たない。

**Snapshot のゲートに切り詰め（truncate）はない。** 日記の側は「到達先が状態ファイルか描画なら破棄、翌日のプロンプトに載るだけなら切り詰め」で線を引いている（docs/diary.md §4）。Snapshot の中身は全項目が Tale コメントへ届くので、この線引きに従えばすべて破棄になる。切り詰めれば、上限を超えたぶんだけ人格が静かに欠けたものが「それらしく見える形」で PixTale へ流れる。

破棄しても失われるものはない。追記のみで、PixTale はバージョンを固定して読むので、直近の安定版が使われ続ける。

## 4.7 作ることと、配ることは別

Snapshot を書いても、**PixTale の出力は1文字も変わらない。** 変わるのは `world/personas.json` が動いたときだけである。

```json
{
  "season": 1,
  "personas": {
    "teo": { "era": "guilds", "version": 2, "path": "characters/teo/snapshots/v0002.json", ... }
  }
}
```

これが**ピン**である。PixTale 側ではなく velum 側に置いてある。理由は2つ。

ひとつは、公開ファイルを raw で取る方式ではディレクトリ一覧が取れないこと。これがなければ向こうは `v0007.json` を直接叩くしかなく、`v0008` が出たことに気づけない。

もうひとつは戻し方である。人格が変になったとき、直すのは PixTale のデプロイではなく、**このファイルの数字ひとつ**になる。Snapshot は追記のみなので、戻す先のファイルは消えていない。ピンは人物ごとに独立していて、ひとりを戻しても他の4人は動かない。

```text
PixTale: personas.json を短い TTL で取得
           → version の指す Snapshot を取得
           → KV へ長い TTL でキャッシュ
```

## 4.8 反映は季ごと

日記は毎日増えるが、配るのは**季の切れ目（25日ごと）**である。1日ごとに人格が動くと、PixTale 側から見れば同じ人物が毎日別人になる。25日で1話ぶんの人生が動く速さがちょうどよい。

季の最終日（第1季は 2026-09-25）に、日次ワークフローが日記を書いたあとコンパイルまで走らせる。この日は5人全員が第5話を書き終えているので、ここより前に圧縮するとその季を生きていない人格ができる。

```bash
npm run snapshot                                # コンパイルする（配らない）
npm run snapshot -- teo                         # ひとりだけ
npm run snapshot -- teo --dry-run               # 何から圧縮するかだけ見る（生成しない）
npm run snapshot -- --publish --season=2        # コンパイルして、そのまま配る
npm run snapshot -- --if-season-end --date=...  # 季の最終日でなければ何もしない（日次から呼ばれる形）
```

**いまは `--publish` を付けていない。** ワークフローはコンパイルまでを自動でやり、配るのは人が読んでからになる。仕様§7 の本丸——「笑いを殺していないか」——が自動で判定できないためである。

人が読む場所は増えていない。季の切れ目は、どのみち次の季の計画（`world/seasons/002/` の5ファイル）を人が読む地点である。

### 全自動にするとき

**ワークフローの1行へ `--publish` を足すだけでよい。**

```yaml
run: npm run snapshot -- --if-season-end --date=${{ inputs.date }} --publish
```

人が介在する箇所は、構造ではなくこのフラグ1つに閉じてある。足した時点で、25日ごとに PixTale の人格が勝手に進む。捨てることになるのは「読まれてから配る」保証だけで、安全側は残る——ゲートに落ちた人物は Snapshot が書かれず、ピンも動かず、前の人格のままになる。

`npm run validate` は、Snapshot の**番号が 1 から飛ばずに並んでいるか**と、**personas.json が実在するファイルを指しているか**を見る。ここが食い違うと、こちらの CI が緑のまま向こうが 404 を踏む。

## 5. Tale コメントでの使われ方

```text
1. カメラで撮影された画像を受信
2. 取得時刻の末尾などから時代を疑似ランダムに決定
3. 時代に対応するペルソナを決定
4. 時代情報と Persona Snapshot を取得
5. 画像と必要最小限のコンテキストを Gemini へ送信
6. ペルソナ固有の Tale コメントを返す
```

PixTale は同じ写真を二度利用できず、画像アップロードもできない。カメラから毎回新しく読み込む仕様なので、同じ画像に同じ時代を再現する決定的ハッシュは不要である。取得時刻を使った簡易な時代選択で足り、世界観上は「撮影した瞬間に、ある時代の Echo と共鳴した」と説明できる。

## 6. 個々の日記を、個々のアイテムへ結び付けない

直近の日記の事件を、すべての鑑定へ強引に接続してはいけない。

作りたい接続は次のものである。

> その人生を送った人物だから、そのアイテムをそのように見る。

**このリポジトリは人生の全記録であり、PixTale が使うのはその履歴から生成された Snapshot だけである。** ここで起きた個々の出来事が、鑑定される個々のアイテムの正史になるわけではない。

## 7. 検収

Snapshot が機能しているかは、記憶なしの従来プロンプトとの比較で判定する。

- 人物固有の着眼点・価値観・口調が出るか
- 日記の一事件へ無理に関連付けず、人生全体から自然に語れるか
- Tale コメントだけを読んで、別の人物とは違う人格を感じるか
- **現行 PixTale の笑い・シェアしたくなる強度を落としていないか**

最後の項目が本丸である。PixTale が止まったのは出力が十分に面白くなかったからであり、育った人格が真面目になりすぎて笑いを殺すのは、この企画の最悪の失敗モードである。

**この検収はまだ行えない。** 日記が1本もない時点でコンパイルできるのは profile と canon の射影までで、「人生が残したもの」と呼べるだけの人生がまだない。14日レビューを通ってから、記憶なしの従来プロンプトと比較する。

各人物の笑いの源泉は `profile.yaml` の `appraisal.humor` に定義してある。声の基準は `tests/fixtures/voice/` にある。
