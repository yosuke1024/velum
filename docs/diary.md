# Diary / Persona Growth

季の計画から取り出したその日の出来事を人物がどう認識したかを生成し、人物状態を更新した上で日記を書く。

**実装状況:** 実装済み。`src/diary/`、`npm run day`。

---

## 1. 流れ

```text
季の計画の1話            その日に何が起きるか（前もって決めてある。docs/seasons.md）
   ↓
人物が認識した事実         同じ出来事でも、誰が見たかで認識が変わる
   ↓
状態の差分                感情・信念・関係・目的の変化。すべて上限つき
   ↓
構造化された人物状態を更新
   ↓
日記を生成                日本語を一次、英語を派生として同時に残す
   ↓
重要な記憶を長期記憶へ
```

## 2. 日記だけを再入力しない

日記だけを再入力して人格を自己更新させる方式は採らない。自己模倣・性格の極端化・反復を起こしやすいためである。

**計画された出来事と構造化された人物状態を正とし、日記は人間向けの主観表現として扱う。** 翌日のプロンプトが読むのは状態ファイルであって、昨日の日記本文ではない（直近の日記は短い要約としてのみ渡す）。

## 3. 5層の状態モデル

安定している順に並べる。

| 層 | ファイル | 安定性 | 書き込むもの |
|---|---|---|---|
| Profile | `profile.yaml` | 永久に固定 | **なし。** 人間だけが編集する |
| Canon | `canon.yaml` | 追記のみ | 1日に最大1件の新事実 |
| Current State | `current-state.yaml` | 日次で変動 | 状態差分 |
| Relationships | `relationships.yaml` | 交流のあった日だけ | 関係差分 |
| Memories | `memories.yaml` | 昇格したときだけ | 1日に最大1件 |

**Profile に書き込み経路を作らない。** 検証ルールで守るのではなく、書き込む手段自体を存在させない。存在しない機能は壊れない。

### 固定するもの / 変えるもの

固定: 根本的な価値観 / キャラクターの魅力の核 / 象徴的な口調 / 外見・職業 / 中核となる願望と恐れ / 物語上の重要な秘密

変える: 現在の感情 / 他者への信頼 / 直近の目的 / 出来事に対する解釈 / 自信・迷い / 習慣 / 誤解・疑念

## 4. 差分は上限つき、超えたら破棄する

モデルは状態の全体ではなく**差分**を返す。すべての差分に上限がある（`src/schemas/limits.ts` の `PATCH_LIMITS`）。

- 関係の `trust` / `wariness` は 0.0–1.0、1日に最大 **±0.05**
- 1日に patch できる関係は最大 **2件**、自分自身は対象にできない
- 特性は最大 **2件** ±0.05、信念は最大 **1件** ±0.1
- 新しい懸念 **2件**、未解決の思考 **2件**
- 新しい記憶 **1件**、新しい canon 事実 **1件**
- 記憶の `importance` は 0.0–1.0。**どれを先に忘れるかを決める重みであり、5段階評価ではない**

**上限を超えた値はクランプせず、その日を破棄する。**

クランプは壊れたプロンプトを「それらしく見える状態」の裏に隠す。欠けた1日は目に見える。だから、状態ファイルか描画に届くものは破棄（fatal）、翌日のプロンプトに載るだけのものは切り詰め（truncate）にする。この線引きは重要度ではなく**到達先**で決まる。

## 5. バリデータが落とせる上限は、すべてプロンプトに書く

**これは硬いルールである。**

バリデータが守っていてプロンプトが伝えていない上限は、厳格なゲートではなく罠になる。モデルは指示に従ったのに1日を失う。

したがってプロンプトは、`src/schemas/limits.ts` の定数から文面を組み立てる。定数を変えればプロンプトも変わる。この対応はテストで固定し、上限を追加してプロンプトに反映し忘れたら CI が落ちるようにする。

破棄になる違反と、切り詰めで済む違反は、プロンプト上で明確に区別して伝える。切り詰めで済むものを「破棄する」と伝えるのは、この節が述べている欠陥を逆向きにしたものであり、失わなくてよい日記を失う。

## 6. 日記の言語

**日本語が一次で、英語が派生。** 品質判定（続きを読みたいか、推したくなるか）は日本語で行う。

```text
characters/<id>/diaries/<YYYY>/<MM>/<YYYY-MM-DD>.ja.md
characters/<id>/diaries/<YYYY>/<MM>/<YYYY-MM-DD>.en.md
```

英語版は翻訳ではなく**文脈変換**とする。条文番号のギャグや値付けの間合いは、直訳すると死ぬ。

本文だけでなく、**サイトが日記ページに出す3つ——タイトル・引用・気分——も同じ回で両方書かせる**（`title_ja`/`title_en`、`quote_ja`/`quote_en`、`mood_ja`/`mood_en`）。日記は毎日出るので、あとから訳す形にすると訳し忘れが英語ページへ積み上がる。片方でも欠ければ、その日は破棄される（本文の下限と同じ扱い）。引用は本文にある一行であって、訳し下ろした別の文ではない——`quote_ja` は `body_ja` から、`quote_en` は `body_en` から引く。

`mood_ja` は `current-state.yaml` に入る値そのものである。プロンプトも状態も日本語で回るので、生成側が読むのは常に ja のほう（`src/lib/bilingual.ts` の `ja()`）。`mood_en` はサイトの表示だけに使う。

`canon_candidate` も同じ回で両方書かせる（`fact_ja`/`fact_en`）。追記された一文は `canon.yaml` に残り、人物ページの「人生の事実」として日本語ページと英語ページの両方に出る。ここを素の日本語で受けていたころは、生成が1件足した日に英語の人物ページへ日本語が出ることになっていた——`CanonSchema` が二言語を必須にしたので、いまは `npm run validate` がこちらで落ちる。

**信念の名前は生成が作らない。** `src/diary/gate.ts` が `current-state.yaml` に無い信念の更新を弾くので、語彙は閉じている（1人3つ、増やせるのは人間だけ）。だから訳は生成させず、`profile.yaml` の `beliefs` が名前と英訳を持ち、`current-state.yaml` は強さだけを持つ。`npm run validate` が両ファイルの集合一致を要求する。サイトの日記ページはこの名前を「この日、動いたもの」の見出しに出すので、訳が欠けると英語ページに日本語が出る。

ウタだけは例外的な扱いが要る。サナ氏族に文字はないので、彼女の日記は「書いたもの」ではなく夜の独白である。本文中で「書く」という語を使わせない。

### 日記の段のモデル

日記は製品そのものであり、季の計画（出来事の設計）とは求める質が違う。`VELUM_DIARY_MODEL` を設定すると日記の段だけそのモデルで書く（`src/diary/generate.ts` の `diaryModel`）。`daily.yml` は repo variable から渡す。使ったモデルは `characters/<id>/events/` の `generation.model` に残るので、切り替えた日を境に読み比べられる。

## 7. レビュー

30日運転すると、各主人公は6本ずつ書く。レビューは 7 / 14 / 30 日目。

確認項目:

- 同じ出来事・感情・表現を反復していないか
- 初期設定から不自然に逸脱していないか
- 人間関係が段階的に変化しているか
- 過去の経験が現在の判断に残っているか
- 日記の続きを読みたくなるか
- キャラクターを推したくなるか
- **5人が違う理由で推せているか**（`profile.yaml` の `appeal_axis` が機能しているか）

最後の項目が最も重要で、同時に自動検証できない。5人が同じ文章構造へ収束するのは、この種の実験で繰り返し観測される失敗である。

## 8. レア表情

各人の口癖・定型はプロンプトで固定し、**その定型が崩れる瞬間を低頻度でだけ許す**（`profile.yaml` の `rare_expression`）。

日記では成長の節目として、Tale コメントではレア演出として機能する。頻発すると価値が死ぬので、出現頻度はゲート側で制御する。

**実装（2026-09-03、diary-v3）。** それまで応答スキーマは `rare_expression_used` を要求していたが、崩れ方そのものを本人に教えていなかったので、常に false だった。いまは:

- プロンプトが `rare_expression` の文面を「定型が崩れる瞬間」として渡し、**崩れるのは感情表現ではなく定型そのもの**（締めが欠ける、注記が付かない、値段が言えない）だと言う。
- `scripts/run-day.ts` が直近 `RARE_EXPRESSION.cooldownEntries` 本（既定 4 本 ≒ 20 日）の `entries/` を見て、崩れがあれば今日は禁止にする。プロンプトはその日の可否を明示し、ゲートは同じ値で判定する——両者がずれれば、指示に従った日を失う（§5 の規律）。
- 許されない日の `rare_expression_used: true` は切り詰めではなく**破棄**。この値は `entries/` とサイトへ届くからである（§4 の到達先の規律）。

## 9. 失敗した日

生成が失敗した日、または上限違反で破棄した日は `characters/*/diaries/` に何も残さず、失敗記録だけを残す。

**季の計画は消さない。** 同じ日をやり直せば、同じ出来事から書き直せる。破棄されたのは日記であって、その日に起きたことではない。

**欠けた日は隠さない。** 反復も、矛盾も、人格の崩壊も、失敗も、等しく実験記録である。

## 10. 形は自由、感情は名指ししない（diary-v3）

最初の3本（9/1 テオ・9/2 リコ・9/3 セヴラン）を読み比べて分かったこと。**声が「形式」の人物はうまくいき、声が「温度」の人物は説明に潰れる。** セヴランは「確認／要検証」と署名という形式が声そのものなので崩れない。テオは鑑定書の締めは出るが、本文で「胸の奥が騒ぐ」「動揺は収まらない」と感情を名指しし、見本にある「別に悔しくはない」という否定で見せる技が出ない。リコは値段先出し・鑑定部・値段で締めは全部出るが、一段落の塊で、自分の矛盾を自分で解説する。

だから diary-v3 で二つを明文化した。

- **感情の名指しを禁じる。** 「胸が騒ぐ」「動揺が収まらない」「不安がよぎる」のような文を書かない。否定・数字・物・手の動きで見せる。「感情を説明せず細部で見せる」だけでは守られなかったので、禁じ手を具体的に書く。
- **形を許す。** 段落を分けてよい、一行だけの段落があってよい、箇条書き・見え消し線・様式（鑑定書・記録・数え上げ）を定型が求めるなら使う。許していなかったから一段落の塊で出た。

温度の人物（リコ・ウタ・カヤ）が形式の人物（セヴラン・テオ）と同じ水準で読めるかどうかは、§7 のレビューで「5人が違う理由で推せているか」の項目として見る。自動では測れない。

## 11. 感情表現は、禁止から混在へ（diary-v4）

§10 の後半を、2026-09-06 に取り消した。

**取り消したのは全人物共通の規則だけである。** 「感情を名指しする文は書かない」は、テオの「胸の奥が騒ぐ」への対処としては正しかったが、5人全員に掛ける規範としては強すぎる。

感情名を全面的に塞ぐと、残る出口は身体感覚と比喩だけになる。5人が揃って「息を呑む」「喉の奥が熱くなる」「雨が窓を叩いていた」の方向へ寄っていく——§7 のレビュー項目でいえば、**5人が同じ文章構造へ収束する**という同じ失敗であって、行き先が違うだけである。禁じ手を1本足したせいで、残った1本が全員の既定になる。

人間の日記はそうなっていない。行動だけを書く日、「怖かった」と平明に書く日、身体の感覚で書く日、何と呼べばいいか分からないまま終わる日が混ざる。

だから diary-v4 の汎用ルールはこうなる。

- 感情の書き方を**ひとつの型に固定しない**。行動 / 平明な感情名 / 身体の感覚 / 曖昧さを、その日と人物に応じて混ぜる。
- **身体の反応を毎回の既定にしない。** 毎日「胸が締め付けられる」なら、それはその人の言葉ではなく型である。
- 天候・物・景色を、毎回その人物の心理の比喩にしない。雨はただの雨でよい。
- 前段で見せたことを、後段で「つまり私は〜だった」と解説し直さない。
- **終わりを毎回、理解・納得・成長・教訓に着地させない。** 分からないまま終わる日があってよい。

否定・数字・物・手の動き（v3 が代わりに置いた手）は消していない。禁じ手の代替ではなく、**選択肢のひとつ**として残る。

### 人物固有の声が、汎用ルールより優先する

これが v4 の要である。プロンプトは「上の書き方より、『話し方』に書いたあなた固有の声のほうが優先される」と明示する。

テオの `profile.yaml` は `voice.register` に「感情を認めない。動揺は『別に悔しくはない』のような否定文と、規約の引用の形でだけ紙面に出る」と書いている。**これは文章規範ではなく人格である。** 汎用ルールが「平明に『怖かった』と書いてよい」と言っても、テオは書かない。緩めたのは全人物に一律で掛かる規範のほうであって、5人それぞれの声ではない。

`tests/unit/prompt-content.test.ts` が、汎用ルールから全面禁止が消えていること・混在の指示が入っていること・テオの「感情を認めない」がプロンプトに残っていることを、それぞれ見ている。

### 足さなかったもの

出来事の側の対応は [seasons.md](seasons.md) §11（Narrative Calibration）。どちらにも次は足していない。

- 日記を生成したあとに全文を書き直す工程
- 「AIらしさ」のスコア、文体語彙の禁止リスト
- 文章の質を理由に日を破棄する新しいバリデータ

§4 の到達先の規律は変わらない。破棄するのは状態ファイルへ届く値の違反であって、**文章の出来ではない**。出来の悪い日は、出来の悪いまま残す（§9）。
